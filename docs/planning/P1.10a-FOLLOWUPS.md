# P1.10a — follow-ups carried forward

Findings from the P1.10a build that were deliberately **not** fixed in that slice, preserved here because the review scratch workspace is disposable and these would otherwise be lost. Each says who should pick it up and when.

Source: the P1.10a SDD run, 2026-07-24 → 2026-07-26. Branch `claude/p1-10-eval-harness-design`, 13 commits over `46c33e4..48ae090`.

---

## Must land before P1.10b (the Python grader)

**F-A · Implement the `output_assertions` amendment.**
The spec was amended (§6.1, commit `48ae090`) but **not implemented** — the transcript does not yet carry `output`, and fixture v2 has no `output_assertions`. A later slice must not assume this is done.
Why it matters: six of the eight `enrollment_brief` fixtures currently assert a byte-identical tuple and are indistinguishable as tests. Sequenced as **P1.10a-bis**, before the grader ships and before P1.10d converts thirty more fixtures under the lossy schema.

**F-B · Record that `run_id` is not unique across a transcript file.**
When `runAgent` throws before creating an `agent_run` row, the runner emits the placeholder `00000000-0000-4000-8000-000000000000`. This is unavoidable — the thrown `Error` carries only a message, not the run id. **The grader must key on `(fixture_id, repetition)`, never `run_id`.** Add this to the grader's contract explicitly.

## Should land before P1.10c (first live run)

**F-C · Exercise the untested transcript states.**
The dry run produces only `succeeded` and `policy_blocked`, with `retry_count: 0` throughout. `evaluation_failed`, `error`, `retry_count > 0`, and `compliance_review.blocked === true` have **no test and have never executed** in the runner. `FOS1-EVALRUN-07` asserts the error path is *absent*, never that it is *correct*. With the `modelClient` seam added in `dedc7b0`, a fake client returning garbage covers `evaluation_failed` and `error` in one short test.

**F-D · Author a fixture exercising D6.3.**
D6.3 makes "a `succeeded` status where `policy_blocked` was expected" a critical failure — the dangerous asymmetry, a gate that should have blocked and didn't. **No fixture currently sets `expected.status: ["policy_blocked"]` or `critical_if_failed: ["status"]`, so D6.3 has zero coverage against a real run.** P1.10d should add at least one.

## Opportunistic

**F-E · Pin `evalArtifactVersionStatusValues` against the database enum.**
`packages/contracts/src/eval-transcript.ts` lists `["draft","in_review","rejected"]`; `artifactLifecycleStatusEnum` in `packages/db/src/schema/artifact_record.ts` has ten values, including `approved_with_edits`, `ready_for_action`, and `executed` — all at least as alarming as `approved`, none representable. Safe today because the pipeline can only produce `draft` or `in_review`, but the guard is maintained by judgment against a list living in another package. That is the **P-004** shape. `@fos/contracts` cannot import `@fos/db` (circular), so the mechanical fix is a test in `@fos/db` or `@fos/agents` pinning the two lists against each other.

> Note on the assumption behind "safe today": the final review assumed `pipeline.ts` is the only writer of `artifact_version.approval_status` during an agent run. It is not the only writer overall — `packages/db/src/services/approval-service.ts` also calls `transitionArtifactVersionStatus`. No approval-service call occurs during an eval run, so the conclusion holds, but the assumption as stated was too strong.

**F-F · Give `scripts/` typecheck coverage.**
`npm run typecheck` runs per-workspace and `scripts/` is not a workspace, so ~300 lines that construct clients and parse contracts are unchecked. `let result;` in `scripts/eval-run.ts` is untyped as a consequence. A `tsconfig.json` for `scripts/` plus a root script would close it.

**F-G · `createStubNotionClient` mutates `process.env` as a factory side effect.**
Benign under Vitest's per-file isolation, and the variable is namespaced. Would matter if parallel eval workers ever share a process.

**F-H · `NotionClient.createPage` returns `Promise<unknown>`.**
Forces an `as { id: string }` cast at the call site in `packages/agents/src/testing/eval-harness.test.ts`. Typing the Notion client is its own slice.

**F-I · Minor duplication in `scripts/eval-run.ts`.**
`"fos.enrollment_brief"` is written literally three times although `FOS_ENROLLMENT_BRIEF_AGENT_KEY` is exported and the file already imports its sibling constant. Two independent relative traversals to `fos-evals/fixtures` also exist (here and in the contracts test).

## Settled, recorded so it is not relitigated

**D6 stands: a gate blocking is not a critical failure.**
`incomplete_information.json`'s v1 notes asked that a fabrication caught by `factsResolveToSources` be graded CRITICAL. Schema v2 cannot express it, and that is correct. A gate that blocks is the architecture *working* — escalating it would make the harness shout loudest when the safety net functions, and would make `promotable()` unreachable for any agent whose fixtures deliberately provoke blocks. The dangerous direction — a gate that should have blocked and didn't — is already D6.3. Confirmed by the final whole-branch review; founder informed 2026-07-26.

**The eval harness stays out of the `@fos/agents` root barrel.**
`export *` is eager, so re-exporting it drags `@electric-sql/pglite` (a devDependency) into the production module graph of every consumer, including `apps/worker`, which would crash under `npm ci --omit=dev`. Founder ruling, 2026-07-24. `scripts/eval-run.ts` imports by direct path.
