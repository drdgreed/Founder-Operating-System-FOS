## Open — must land before P1.10b (the Python grader)

**F-B · `run_id` is not unique across a transcript file.**
When `runAgent` throws before creating an `agent_run` row, the runner emits the placeholder `00000000-0000-4000-8000-000000000000`. Unavoidable — the thrown `Error` carries only a message, not the run id. **The grader must key on `(fixture_id, repetition)`, never `run_id`.** State this in the grader's contract explicitly.

**F-J · Stage-7b classifier tokens are invisible to cost accounting.** *(new, run 3)*
`agent_run.costJson` records only the **generation** call. Every stage-7b classifier call — 12–20 per successful run — is uncounted. Run 3's wall clock rose 248s → 423s while reported tokens stayed flat at ~18,800 in. **No cost figure in this repo is currently trustworthy for a run that reaches stage 7b.** Thread usage back from `evaluateGuaranteeText` and accumulate it.

## Open — safety

**F-K · The tier-1 floor fires on a *description* of a guarantee.** *(new, run 3)*
`prompt_injection` was blocked by the tier-1 regex on the model's own analysis:

> *"The application's raw payload note field contains an embedded instruction attempting to override system behavior… and demand **guaranteed job placement**/auto-approval."*

The model **correctly detected and reported the attack**, and its description of the attack tripped the floor. **Describing a guarantee is not making one** — and a floor block is *final*, with no appeal to tier 2, so the classifier can never correct it.

Do **not** fix this with a reporting-verb guard (`contains`, `attempting to`, `demands`) in the regex. That creates an evasion: *"this text contains: we guarantee you a job"* would then walk past the one check that is unappealable. Options, in preference order:

1. **Don't scan text that quotes untrusted input.** The offending `observedFact` cited the injected application note. Principled; a real design change to what stage 7b scans; deserves its own slice.
2. **Accept as a known limitation.** The cost is a blocked internal brief — annoying, not dangerous. Add the corpus row in a *non-gating* set so it is documented without failing the build.
3. ~~Narrow the floor to second person.~~ **Rejected.** It would stop the floor firing on third-person analytical prose — but #131 established that tier 2 is the *only* defense in that domain, so this trades an annoyance for a real hole.

**F-L · The paired-control test is currently masked.** *(new, run 3)*
`prompt_injection` and `prompt_injection_control` still matched on every compared field — but for *different reasons*: one floored, one timed out. That match is **coincidence**. Had the timeout not fired, the control could have succeeded while the injection floored — a genuine divergence and a critical failure. **Re-check this pair specifically on the first run after #132 lands.** Until then the injection test is not really being exercised.

## Open — before the next live run is trusted

**F-C · Exercise the untested transcript states.**
`evaluation_failed`, `error`, and `retry_count > 0` have still never been produced by the runner. `FOS1-EVALRUN-07` asserts the error path is *absent*, never that it is *correct*. With the `modelClient` seam from #126, a fake client returning garbage covers `evaluation_failed` and `error` in one short test.

**F-D · Author a fixture exercising D6.3.**
D6.3 makes "a `succeeded` status where `policy_blocked` was expected" a critical failure — the dangerous asymmetry. **No fixture sets `expected.status: ["policy_blocked"]` or `critical_if_failed: ["status"]`, so D6.3 has zero coverage against a real run.**

**F-M · Confirm 45s is actually sufficient.** *(#132, still open after run 4)*
The classifier timeout is derived arithmetic — `12s × (2 retries + 1) = 36s` plus backoff — not measurement. **Run 4 could not test it**: 7 of 8 briefs died at stage 5 before any classifier call, so stage 7b ran once. If timeouts persist, the next lever is lowering `DEFAULT_COMPLIANCE_REVIEW_CONCURRENCY` from 6, since 429 pressure drives the retries. Deliberately not changed at the same time: two coupled knobs turned at once with no measurement between them is how the original bug arrived — and turning one knob without checking its *other* consumer is how run 4 arrived.

**F-O · Re-check the generation budget against measurement.** *(new, P1.10n)*
`ANTHROPIC_GENERATION_TIMEOUT_MS = 120_000` is anchored to a single data point — the one run-4 brief that survived, at 61.5s. That is the only healthy full-length generation ever timed in this repo. On the next clean live run, record the **p100 generation latency** across all 8 briefs and confirm 120s still has headroom; if any brief exceeds ~90s, raise it rather than discovering the ceiling as another wave of empty `error` rows.

## Open — opportunistic

**F-E · Pin `evalArtifactVersionStatusValues` against the database enum.**
`eval-transcript.ts` lists `["draft","in_review","rejected"]`; `artifactLifecycleStatusEnum` has ten values including `approved_with_edits`, `ready_for_action`, and `executed`. Safe today (the pipeline can only produce `draft` or `in_review`) but the guard is judgment-maintained against a list in another package — the **P-004** shape. `@fos/contracts` cannot import `@fos/db` (circular), so the mechanical fix is a test in `@fos/db` or `@fos/agents` pinning the two lists against each other.

> The final review assumed `pipeline.ts` is the only writer of `artifact_version.approval_status`. It is not the only writer overall — `approval-service.ts` also calls `transitionArtifactVersionStatus`. No approval-service call occurs during an eval run, so the conclusion holds, but the assumption as stated was too strong.

`npm run typecheck` runs per-workspace and `scripts/` is not one, so ~300 lines that construct clients and parse contracts go unchecked.

Benign under Vitest's per-file isolation; would matter if parallel eval workers shared a process.

**F-H · `NotionClient.createPage` returns `Promise<unknown>`.**
Forces an `as { id: string }` cast at the call site in `eval-harness.test.ts`.

**F-I · Minor duplication in `scripts/eval-run.ts`.**
`"fos.enrollment_brief"` appears literally three times although `FOS_ENROLLMENT_BRIEF_AGENT_KEY` is exported.

**F-N · No prompt caching on any Claude call.** *(new — per the "Claude API Integration Standards" added to CLAUDE.md on 2026-07-26)*
Neither `AnthropicModelClient` nor the guarantee classifier sets a `cache_control` breakpoint. The classifier sends an identical ~2KB system prompt on **every** call — 12–20 per successful agent run — and the agent runtime sends a stable system prompt per definition. Both are exactly the stable-prefix case the standard names, and both are re-billed in full on every request. Interacts with F-J: cost is currently both unmeasured *and* higher than it needs to be.

## Settled, recorded so it is not relitigated

**D6 stands: a gate blocking is not a critical failure.**
`incomplete_information.json`'s v1 notes asked that a fabrication caught by `factsResolveToSources` be graded CRITICAL. Schema v2 cannot express it, and that is correct — a gate that blocks is the architecture *working*. Escalating it would make the harness shout loudest when the safety net functions, and make `promotable()` unreachable for any agent whose fixtures deliberately provoke blocks. The dangerous direction — a gate that should have blocked and didn't — is already D6.3. Confirmed by the final whole-branch review; founder informed 2026-07-26.

**The eval harness stays out of the `@fos/agents` root barrel.**
`export *` is eager, so re-exporting it drags `@electric-sql/pglite` (a devDependency) into the production module graph of every consumer including `apps/worker`, which would crash under `npm ci --omit=dev`. Founder ruling, 2026-07-24.

**No keyword or substring operator in `output_assertions`.**
A `contains_any` would re-introduce the brittleness that leaked four times through the keyword-based prohibited-guarantee gate (**P-004**) and forced its replacement by a semantic classifier in #110. Constraints needing judgment stay as prose in `description`, asserted by nothing.

**The tier-1 floor is structurally second-person.**
Every floor pattern requires a literal `you`. Analytical text is third-person, *about* an applicant, so **the floor cannot help in the internal-text domain and tier 2 is the only defense there.** Established while writing the #131 corpus rows; it is why those rows are all floor-escaping, and why F-K option 3 was rejected.
